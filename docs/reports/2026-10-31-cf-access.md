# CF-only access pilot: implementation and local verification

Date: 2026-10-31. Baseline: `4330d69`. Status: **implemented and locally verified;
not committed, pushed, deployed, or accepted on a mainland China Telecom network**.

## Delivered

- Opt-in subscription-level `cfOnly` and zero-to-three `cfPreferredIps`, with an
  additive migration and unchanged defaults for existing subscriptions.
- Managed VLESS+WS+TLS-only selection; literal CF IPv4/IPv6 allowlisting,
  canonicalization, duplicate/private/mapped-address rejection and bounded DNS.
- Pinned CF default address plus preferred endpoint aliases. Original SNI,
  WebSocket Host/path, port, credentials and certificate checks are preserved.
- Ordered Mihomo fallback, sing-box/HomeProxy URLTest, and URI variants, with
  owner/share parity across all four formats. No active safe endpoint fails
  closed rather than generating a DIRECT fallback configuration.
- Owner-scoped, concurrency-bounded exact-endpoint E2E check, explicitly marked
  PANEL. Origin-risk findings remain UNVERIFIED; ordinary node health is not
  overwritten. Shared CF-only metadata omits the origin server IP field.
- Desktop/mobile controls, error display, and rollback by clearing preferred
  endpoints without removing CF-only protection or rotating subscription tokens.
- No remote service deployment, DNS mutation, firewall change or production
  database migration was performed.

## Remaining acceptance and release constraints

1. Explicit commit/push/deploy authorization and the normal protected release
   workflow remain outstanding.
2. Audit the actual pilot origin: independent entry/exit IPs, DNS-only siblings,
   other direct services, historical exposure and CF-only ingress firewall/TLS
   policy. The new panel check is not proof that the origin is hidden.
3. Select working candidate IPs on the user's actual mainland China Telecom
   connection; none have been automatically promoted based on overseas tests.
4. Run peak/off-peak connection, throughput, long-session and CF-only failure
   tests with an agreed traffic budget; observe for 24-48 hours.
5. Prefer clearing candidates for rollback. An application version predating
   CF-only ignores its protection, so do not use that as an unguarded live
   rollback. Keep a feature-aware rollback build or block affected export routes
   before older-code rollback. Existing clients must refresh downloaded configs.

See `docs/RUNBOOK-cf-access.md` for configuration, evidence boundaries and the
production acceptance/rollback procedure.
